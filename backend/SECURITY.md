# Security Audit — geo-alert backend

Audit date: 2026-05-05  
Scope: Go + Gin backend (`internal/handler/`, `internal/middleware/`, `internal/auth/`, `cmd/server/main.go`, `pkg/storage/`)

---

## Findings and fixes

### Fixed

**1. Missing security headers**
No HTTP security headers were set on any response, leaving clients without standard browser-level protections.

Added `internal/middleware/security_headers.go` with the following headers applied globally:
- `X-Content-Type-Options: nosniff` — prevents MIME-sniffing
- `X-Frame-Options: DENY` — prevents clickjacking
- `X-XSS-Protection: 1; mode=block` — legacy XSS filter for older browsers
- `Referrer-Policy: strict-origin-when-cross-origin` — limits referrer leakage

**2. Missing CORS policy**
The server accepted cross-origin requests without any `Access-Control-Allow-Origin` header, meaning browsers would block legitimate frontend requests while the server had no origin restriction at the network level.

Added `internal/middleware/cors.go` with an allowlist-based CORS middleware. Allowed origins are configured via the `CORS_ALLOWED_ORIGINS` environment variable (comma-separated; default: `http://localhost:5173`). Preflight `OPTIONS` requests are short-circuited with `204 No Content`.

**3. CORS_ALLOWED_ORIGINS missing from config**
`config.go` had no field for CORS origins, making it impossible to configure allowed origins from the environment.

Added `ServerConfig.CORSAllowedOrigins []string` populated from `CORS_ALLOWED_ORIGINS`.

### Already correct — no changes needed

**JWT algorithm check**
`internal/auth/jwt.go` (`ValidateAccessToken`) already validates `t.Method.(*jwt.SigningMethodHMAC)` before using the secret, preventing "alg: none" attacks.

**Magic bytes validation on file upload**
`internal/handler/upload.go` validates JPEG (`\xFF\xD8\xFF`), PNG (`\x89PNG`), and WebP (`RIFF....WEBP`) magic bytes independently of the `Content-Type` header. File names are UUID-generated by `pkg/storage/client.go`, eliminating path traversal risk.

**Input length limits**
- `marker.go`: title capped at 200 runes, max 5 images, max 5 tags
- `user.go`: `display_name` capped at 100 runes, `bio` at 150 runes

**SQL injection**
All raw SQL in `internal/repository/` (GORM `.Raw()` / `.Exec()`) uses `?` positional placeholders exclusively. No string concatenation of user input into queries was found.

**Rate limiting**
`internal/middleware/ratelimit.go` applies a sliding-window rate limit globally (60 req/min) and per critical endpoints (e.g., `POST /auth/google` at 10/min).

**Open redirect**
`redirect_uri` in `POST /auth/google` is passed directly to Google's OAuth token exchange endpoint as required by the OAuth 2.0 spec; Google validates it against the registered URIs for the client ID. It is not used for server-side redirects.

## Known limitations

**Rate limiting is IP-based only**
Authenticated endpoints are rate-limited by IP address, not by `user_id`. An attacker controlling many IPs can bypass per-IP limits. Migrating to user-ID-based limits for authenticated routes would require passing the resolved user ID into the rate limiter after the auth middleware runs. This is a known trade-off accepted for the current scope.

**No HSTS header**
`Strict-Transport-Security` is intentionally omitted because TLS termination is expected to happen at the reverse proxy / load balancer layer (nginx / Cloud Run), not at the Go server. HSTS should be set there.

**`AllowCredentials` not set**
The CORS policy does not set `Access-Control-Allow-Credentials: true` because the API uses `Authorization: Bearer` tokens (not cookies), so credentials mode is not needed.
